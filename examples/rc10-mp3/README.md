# rc10-mp3

An MP3 player in the Celoxica RC10's FPGA, built in milestones
(`docs/mp3-decoder-plan.md`). The PC streams the MP3 file itself over USB;
the FPGA decodes it (MPEG-1 Layer III, 32/44.1/48 kHz, every mode) and
plays it through the board's audio output.

```sh
fpgaflow -C examples/rc10-mp3 build
fpgaflow-celoxica load examples/rc10-mp3/build/impl/mp3_top.bit
fpgaflow-celoxica play song.mp3      # anything else is converted to MP3 by ffmpeg
```

`play` checks which design is loaded: with this one, an MPEG-1 Layer III
file is sent as it is (a leading ID3v2 tag is skipped); anything else (WAV,
FLAC, MPEG-2/2.5 "LSF" MP3s at 8-24 kHz, ...) is converted by ffmpeg with
LAME to 192 kbit/s MPEG-1 at 44.1 kHz on the way. The decoder resynchronises
after damage: a header counts only when the next one follows where its
length says.

Joystick: up/down = volume (16 steps of 3 dB, shown on the display), left/
right = DAC coding (NRZ or return-to-zero, LED 1), centre = pause (the dot).

The decoder is bit-exact with the fixed-point model in `crates/mp3model`
(26-bit data, 18-bit coefficients: ISO 11172-4 "full accuracy" on all the
test streams), checked stage by stage in simulation and on the board.

## Milestone 1: the front end

`mp3_frontend` turns the byte stream into MPEG-1 Layer III frames:

- Bytes go into a 4 KB ring buffer; FULL pauses the PC when it fills.
- A header counts only if the next header follows where its length says
  (or the stream ends there); otherwise the search moves on a byte. This
  resynchronises after damage and skips anything that isn't audio.
- The side information is parsed one bit a cycle; the main data is appended
  to the 4 KB bit reservoir, and each frame's main data start is worked out
  from `main_data_begin`.
- Each frame produces a 70-byte record (header, every side-info field,
  reservoir pointer; layout in `crates/mp3model/src/frontend.rs`) with a
  running CRC-32.

Checked against the golden model (`crates/mp3model`):

```sh
tools/mp3-test-streams.sh MUSIC.wav          # from the repository root
cargo build --release -p fpgaflow-mp3model
examples/rc10-mp3/tools/make-vectors.sh      # 18 streams, ~5000 frames
fpgaflow -C examples/rc10-mp3 sim            # every record must match
```

and on the board:

```sh
fpgaflow -C examples/rc10-mp3 build
fpgaflow-celoxica load examples/rc10-mp3/build/impl/mp3_top.bit
fpgaflow-celoxica mp3-check song.mp3        # frames, bytes and CRC vs the model
```

LED 0 is lit when the stream is idle, LEDs 4-7 show the input buffer
filling.

## Milestone 2: scale factors and Huffman decoding

`mp3_granule` takes each frame's side info from the front end (which stays
at most one frame ahead, so the reservoir is never overwritten under it) and
reads the reservoir bit by bit:

- scale factors in all three layouts (long, short, mixed), with scfsi
  reusing granule 0's, kept in small LUT RAMs;
- the 576 Huffman values per granule: big-value pairs in three regions
  (linbits, signs), then count1 quadruples up to part2_3_length (one that
  runs past the end is dropped), the rest zero. The codes are walked one
  node per cycle through binary trees in block RAM (`huff_rom.sv`, 1393
  nodes, generated with `mp3model rtl-tables examples/rc10-mp3/rtl` from the
  model's own tables, like `mp3_tables.sv`).

Each granule gives a record (61 scale factors, 576 values) with a running
CRC-32. The testbench compares every scale factor and value with the model;
`mp3-check` compares granule counts and the CRC on the board. The project
simulates in Verilator: the 18 vector streams (5160 frames, 17270 granules)
take about 3 minutes there, about 35 in Icarus.

## Milestone 3: requantise, stereo, reorder, antialias

`mp3_spectral` takes each granule's records from `mp3_granule` and works in
26-bit fixed point (3 integer bits; coefficients 18-bit with 17 fraction
bits), bit-exact with the fixed-point model (`crates/mp3model/src/fixed.rs`):

- requantise: |n|^(4/3) from an 18-bit mantissa / 4-bit exponent table
  (n < 1024; above, entries k and k + 1 interpolated in integers), times
  2^(k/4), shifted, rounded, saturated;
- stereo: intensity above the right channel's last non-zero band (per window
  for short blocks), mid/side elsewhere;
- antialias butterflies; short blocks are read out through a reorder map.

One 27 x 19 multiplier is shared by all three. Each granule and channel gives
576 values (the IMDCT's input) with a CRC; the testbench compares every value
with the model, `mp3-check` the counts and CRC on the board. All tables are
generated by `mp3model rtl-tables` from the model's own data.

## Milestone 4: IMDCT, windows, overlap-add, frequency inversion

`mp3_imdct` takes each channel's 576 values and, per subband, computes the
36-point IMDCT directly (36 outputs of 18 terms; short blocks three 12 x 6
windows overlapping in z) with one pipelined 26 x 18 MAC over a ROM of cosine
x window coefficients (`mp3_imdct_rom.sv`, 2016 entries). It adds the previous
granule's second half (2048 x 27 overlap RAM), keeps the new one, and negates
odd samples of odd subbands.

The stages hand records on with ready/valid; a stage is ready only before a
record's first byte (a stage whose data lag its state by a cycle could
otherwise start the next record early).

## Milestone 5: polyphase synthesis and the audio output

`mp3_synth` takes both channels of a granule (576 subband samples each) and,
for each of the 18 time slots and each channel, shifts the 1024-entry V ring
by 64, computes the 64 new V values (32-term MACs against N[i][k] =
cos((16 + i)(2k + 1) pi / 64), which is just a 128-entry cosine table), then
the 32 PCM samples (16 terms each against the standard's window D), rounded
and clamped to 16 bits. Stereo words go into a 1024-word dual-clock FIFO.

Decoding is paced by that FIFO: the synthesis waits for room for a time
slot, which stalls every stage before it and finally the USB bus (FULL), so
the PC streams at playback speed. (While FULL holds the PC off, the 22 ms
end-of-stream timer doesn't run.)

The audio side is the PCM player's: second-order sigma-delta DACs (RZ coding,
no hiss), volume, pause. Each FIFO word carries its stream's rate; the DAC
clock is a BUFGMUX of clock A (two DCMs, 48 x 21/20 x 7/8 = 44.1 MHz) for
44.1 kHz and the FX2's 48 MHz for 48 kHz (1000 clocks a sample) and 32 kHz
(1500), so all three rates are exact. It switches when the first word of a
new rate reaches the DACs.

`mp3-check` compares every stage (frames, granules, spectra, subband sets,
PCM samples, each with a CRC) with the model, and now plays the stream as it
goes; `mp3-play FILE` only plays. Status bytes 50-62 add the PCM count and
CRC, underruns, the PCM FIFO fill, the controls and the playing rate
(`rtl/mp3_top.sv`).

Results: the 18 vector streams (5160 frames, 9.9 million PCM samples) match
the model in simulation and on the board, as do the 45 generated test
streams and a full 4:16 track (PCM CRCs, played in real time with no
underruns); 7.0k slices (52%), 31 of 32 block RAMs, 14 multipliers; 48 MHz
with 0.75 ns to spare. Simulation now takes 1.5 hours for the full set
(`build/vectors/list.txt` can name a subset; the IMDCT and synthesis are
most of it).
